# Love-Kitchen 爆款产品审视与改造计划

> 视角：挑剔用户 + 资深互联网产品经理 + 全栈工程师 + UI/UX 设计师
> 结论用途：给 Cursor 继续执行，优先做能提升下载、留存、付费意愿的改造。

---

## 0. 一句话结论

Love-Kitchen 已经不是普通菜谱 App，它真正有潜力的差异点是：

**把“家里有什么、快过期什么、今晚吃什么、还缺买什么、做完扣掉什么”串成家庭厨房闭环。**

但如果按爆款产品审视，目前还差两口气：

1. **Aha moment 不够快**：用户第一次打开后，不能在 60 秒内强烈感到“它真的帮我少想一顿饭”。
2. **信任闭环还没稳**：家庭同步、catalog ID、购物清单删除、同步回声这些问题会破坏“我敢长期用它管冰箱”的信任。

所以不要继续堆功能。下一轮应先做：

**修可信基础 → 强化首日体验 → 把“今晚一餐”做成主产品 → 精简旁枝 → 再考虑付费。**

---

## 1. 挑剔用户视角：它现在让我想用吗？

### 1.1 目前最能打动人的亮点

- **冰箱可视化有记忆点**：不是一张普通列表，而是“我家的冰箱”。这比泛菜谱推荐更有情感锚点。
- **临期食材 + 今晚方案是高频痛点**：用户不是缺菜谱，而是缺“现在该怎么处理冰箱里的东西”。
- **拍照/小票识别方向很对**：降低录入成本，这是冰箱类产品能不能活下去的关键。
- **家庭共享有潜在付费价值**：一个人用是工具，两个人用才变成家庭协作。
- **烹饪扣减是闭环**：只推荐不扣减，就永远停在内容消费；扣减后才像一个厨房系统。

### 1.2 目前会让我犹豫的点

- **第一次使用门槛仍偏高**：如果要我手动维护冰箱，我会想“算了”。必须让拍小票/拍冰箱/示例冰箱成为首屏路径。
- **AI 推荐的可信度需要被解释**：用户会问“这是随便编的吗？”需要展示“用了哪些现有食材、哪些临期、缺哪些要买”。
- **同步问题会直接毁信任**：采购项删不掉、刷新后又回来，用户会立刻放弃。
- **功能名有点散**：首页、今晚、冰箱、我的都在做事，但爆点应集中在“今晚吃什么”。
- **付费欲望还不够强**：现在更像愿意试用的小程序；要让人付费，需要云同步、家庭协作、AI OCR、周计划这些稳定高价值能力。

### 1.3 当前下载/使用/购买欲望评分

| 维度 | 当前评分 | 原因 |
|---|---:|---|
| 愿意首次打开 | 7/10 | 视觉和概念有趣，“冰箱+AI”有吸引力 |
| 愿意坚持使用一周 | 5/10 | 录入、同步、推荐可信度还会阻碍习惯形成 |
| 愿意分享给家人 | 6/10 | 家庭厨房方向好，但同步可信度必须先修 |
| 愿意付费 | 4/10 | 还没形成不可替代的连续价值 |

爆款标准下，目标应是：

- 首次打开：8.5+
- 一周留存：7+
- 家庭分享：8+
- 付费意愿：6.5+ 起步

## 2. 产品经理视角：爆款应抓哪条主线？

### 2.1 不要把它定位成“AI 菜谱”

“AI 菜谱”太泛，用户已经不缺菜谱，也不缺搜索入口。竞品和同类产品普遍覆盖按食材找菜、周计划、购物清单、营养/偏好、菜谱收藏等能力，例如 SuperCook、Samsung Food、Mealime、SideChef 都在围绕“食材/计划/购物”做闭环。

Love-Kitchen 更好的定位是：

**家庭冰箱管家：拍一下库存，今晚吃什么自动排，快过期前提醒，全家共用一张采购清单。**

### 2.2 北极星指标

建议只选一个北极星：

**每周成功解决的家庭晚餐次数。**

一次“成功解决晚餐”定义为：

1. 用户从冰箱/小票/手动选择食材进入今晚方案；
2. 生成至少 1 套可做方案；
3. 用户打开详情或烹饪模式；
4. 至少扣减 1 个食材，或生成/同步采购清单。

### 2.3 首日 Aha moment

目标：用户首次进入后 60 秒内完成：

**录入/载入 5 个食材 → 看到 3 套今晚方案 → 知道先消耗什么 → 生成缺货采购清单。**

不要让用户第一眼看到“泛推荐流”。第一眼应该是可行动的厨房：

- 家里有什么？
- 快过期什么？
- 今晚可以做什么？
- 缺什么要买？

## 3. UI/UX 设计师视角：高级感在哪里，哪里还像补丁？

### 3.1 值得保留的审美资产

- **暖灰纸感 + 绿色厨房感**：比常见 AI 紫色渐变更生活化。
- **冰箱柜体视觉**：这是产品识别资产，应继续强化。
- **卡片文案有温度**：不像纯工具，适合家庭场景。
- **临期/今晚/采购清单联动**：这是交互价值，不只是 UI 装饰。

### 3.2 需要收敛的视觉问题

- **页面密度不统一**：有的页面像生活方式 App，有的像开发调试工具。
- **样式体系仍有旧痕迹**：`D`、旧 `common.ts` 色值、残留样式并存。
- **图标和按钮语言不统一**：有些地方是文字按钮，有些地方是符号，有些地方像临时占位。
- **普通用户不该看到工程配置感**：如“未配置远端同步”“TARO_APP...”这类信息应只在开发者区出现。

### 3.3 设计目标

做成“高级但高效”的家庭工具，不做营销页式花架子。

设计关键词：

- 温暖、可信、清爽、有秩序
- 像一个懂生活的厨房助手
- 少解释，多给下一步
- 每个页面只有一个主动作

## 4. 全栈工程师视角：先修哪些硬伤？

这些不是“优化项”，而是信任基础。建议 Cursor 第一阶段先做。

### P0-1 家庭同步必须加身份校验

现状：

- `api/household-sync.js` 的 `pull/push` 只要有 `householdId` 就能读写。

风险：

- 家庭冰箱和采购清单属于隐私数据。
- 一旦 ID 泄露，就能读写整份家庭数据。

改造建议：

- `create/join` 后返回 `memberToken`。
- 服务端保存 member token hash。
- `pull/push` 必须携带 `householdId + memberId + memberToken`。
- 不通过则 401。

验收：

- 无 token 的 pull/push 返回 401。
- 错 token 返回 401。
- join 后 token 可正常 pull/push。

### P0-2 修复 catalog 运行时 ID 与分片原始 ID 不一致

现状：

- `catalogLoader` 为避免 legacy 冲突，给 catalog-only 菜谱重写了运行时 ID。
- 但详情加载 chunk 后返回原始 ID。

风险：

- 收藏、做过、分享 fallback 会错指到 legacy 菜。
- 用户从列表点 A，详情/分享可能变成 B。

改造建议：

- 详情返回 chunk full recipe 时保留 `lite.id`。
- 增加 `catalogId` 或 `remoteId` 存原始 ID。
- 所有用户侧状态使用稳定运行时 ID。

验收：

- 从 catalog 列表打开详情后，详情 `recipe.id` 与列表一致。
- 收藏状态在列表与详情间一致。
- 分享 fallback 不会打开 legacy 冲突菜。

### P0-3 家庭购物清单删除必须能同步

现状：

- 客户端删除已勾选项后 push。
- 服务端 `mergeShoppingList` 用旧清单和新清单按名称合并。
- 缺失项不会被删除，下一次 pull 又回来。

改造建议：

低复杂度方案：

- `shoppingList` 采用客户端当前列表覆盖。
- 依赖 `updatedAt` 做最后写入胜出。

更稳方案：

- 每个 item 加 `deletedAt` 墓碑。
- 服务端按 `id` 合并，保留较新的 item 状态。

验收：

- A 删除采购项后 push，B pull 后该项消失。
- 删除后再次刷新不会复活。

### P0-4 pull 不应触发无意义 push

现状：

- `pullRemote -> applyHousehold -> pantry.replaceItems`。
- `bindPantry` 的 reaction 监听 pantry 变化后自动 push。

风险：

- 用户只是刷新，也会把远端数据再写回去。
- `updatedBy` 可能被误改成本人。

改造建议：

- 增加 `suppressNextPantryPush` 标志。
- apply remote pantry 时临时关闭自动 push。
- 或对 pantry snapshot 做深比较，无变化不 push。

验收：

- pull 后不会立刻调用 push。
- 本地手动增删改仍会 debounce push。

## 5. 爆款功能改造优先级

### Epic A：可信同步与数据正确性

目标：

让用户敢把真实冰箱和家庭采购清单交给它。

范围：

- 家庭同步鉴权。
- catalog 稳定 ID。
- 购物清单删除同步。
- pull/push 回声抑制。
- 增加回归测试脚本。

建议 Cursor 提示：

> 先执行 `docs/Love-Kitchen-爆款产品审视与改造计划-2026-07-05.md` 的 Epic A。只修数据正确性和同步安全，不改 UI，不新增业务功能。每个 P0 问题都要加回归检查。

完成标准：

- `npm run typecheck`
- `npm run test:regression`
- `npm run build:weapp`
- 新增 regression 覆盖上述 4 个问题。

### Epic B：首日 Aha onboarding

目标：

用户 60 秒内看到“今晚可以吃什么”。

建议改造：

1. 首页首屏改成“厨房状态面板”：
   - 今日可做方案数量。
   - 快过期食材数量。
   - 缺货采购数量。
   - 主 CTA：`拍小票/拍冰箱` 或 `今晚吃什么`。
2. 新用户提供三条路径：
   - 拍小票/拍冰箱导入。
   - 手动添加 5 个常见食材。
   - 使用示例冰箱体验。
3. 首次完成录入后自动跳到今晚方案。
4. 方案页解释推荐依据：
   - 已用冰箱食材。
   - 优先消耗临期。
   - 还缺采购项。

验收：

- 空用户不再看到泛推荐为主。
- 新用户 3 步内能得到今晚方案。
- 未配置 AI 时仍有本地示例路径。

### Epic C：把“今晚一餐”做成主产品

目标：

从“推荐几道菜”升级为“解决一顿饭”。

建议改造：

- `pages/pick` 和 `pages/result?from=meal` 统一成主流程。
- 每个 meal plan 必须有：
  - 主菜/素菜/汤或快手菜角色。
  - 总时间。
  - 使用现有食材数量。
  - 临期消耗比例。
  - 缺货清单。
- 详情页烹饪完成后：
  - 扣减食材。
  - 更新家庭购物清单。
  - 记录“解决了一顿饭”事件。

验收：

- 从冰箱临期卡片、首页 CTA、提醒落地都进入同一 meal 流。
- 用户能一键把缺货项加入家庭采购清单。
- 做完后冰箱状态变化可见。

### Epic D：视觉与交互收敛

目标：

去掉补丁感，形成高级、可信、统一的厨房工具。

建议改造：

- 清理 `tokens.ts`、旧 `common.ts` 色值和首页遗留样式。
- 统一按钮层级：
  - 主动作：绿色实心。
  - 次动作：浅绿色/描边。
  - 危险动作：红色。
  - 工程/开发动作：只在 DevTools。
- 统一四个 tab 的页面结构：
  - 顶部状态/标题。
  - 一个主任务区。
  - 次级列表或卡片。
- 普通用户界面去掉配置说明。
- 家庭厨房未配置远端时，不展示“本地家庭”作为正式能力，可改为“家庭同步即将可用”或仅开发环境显示。

验收：

- 普通用户看不到 `TARO_APP`、`未配置 API` 等工程语言。
- 首页、今晚、冰箱、我的的按钮和卡片风格一致。
- 删除无引用样式/主题文件后 typecheck 通过。

### Epic E：分享、留存、付费准备

目标：

形成自然传播和付费理由。

建议改造：

1. 分享卡片分三类：
   - 今晚菜单：`今晚吃 X，还缺 Y 样`。
   - 家庭邀请：`加入我家的厨房清单`。
   - 采购清单：`帮我买这 N 样`。
2. 留存触发：
   - 临期提醒。
   - 每周菜单建议。
   - 家庭成员更新采购清单通知。
3. 付费能力先埋点不急着收费：
   - 云端家庭同步。
   - AI OCR 高额度。
   - 周菜单自动规划。
   - 多家庭/多冰箱。
   - 历史数据与营养偏好。

建议商业化：

- 免费：本地冰箱、基础推荐、少量 OCR、基础提醒。
- Plus：家庭云同步、无限 OCR、周计划、家庭采购协作。
- 家庭版：多人共享、多个冰箱、成员操作记录。

不要过早弹付费墙。应在用户完成 3 次晚餐闭环后再提示升级。

## 6. 应该精简或隐藏的功能

### 建议弱化

- **天气推荐**：可以保留，但不该是核心卖点。天气影响晚餐决策的权重低于“冰箱有什么”。
- **泛菜谱浏览**：保留搜索即可，不要让首页变成菜谱信息流。
- **AI 生成指定菜**：作为兜底，不要主推。真实菜谱库和厨房闭环更可信。
- **开发者工具**：只在开发/体验版或隐藏入口展示。

### 建议移除或合并

- 未使用主题文件、旧首页 deck 样式、重复 storage 工具。
- 普通用户可见的“未配置远端同步”说明。
- 没有真同步能力时的“本地家庭”正式入口。

### 不建议继续堆的功能

- 社区动态。
- 大而全营养报表。
- 菜谱内容流运营。
- 复杂会员体系。
- 多端账号体系。

这些会稀释核心闭环。

## 7. 推荐路线图

### 第 1 周：修可信基础

- 完成 Epic A。
- 不改大 UI。
- 所有修复有 regression。

结果：

- 数据不会错。
- 家庭同步有基本安全。
- 可以开始真机内测。

### 第 2 周：做首日 Aha

- 完成 Epic B。
- 首页从“推荐内容”改为“厨房状态 + 今晚行动”。
- 新用户支持示例冰箱体验。

结果：

- 用户第一次打开就知道产品价值。

### 第 3 周：强化今晚一餐

- 完成 Epic C。
- 统一 meal 流。
- 做完扣减、缺货采购、家庭共享打通。

结果：

- 产品从工具变成习惯。

### 第 4 周：视觉收敛和分享

- 完成 Epic D + Epic E 的分享部分。
- 清理补丁感。
- 做可传播分享卡。

结果：

- 更像一个可上线、可传播、可付费的产品。

## 8. 爆款判断清单

Cursor 每完成一轮后，用这张表验收：

| 问题 | 目标答案 |
|---|---|
| 用户 60 秒内能看到价值吗？ | 能，导入/示例后直接出今晚方案 |
| 用户知道为什么推荐这些菜吗？ | 能，显示现有食材、临期、缺货 |
| 用户做完一顿饭后数据会变吗？ | 会，扣减冰箱并更新历史 |
| 家人能协作吗？ | 能，安全同步采购清单和冰箱 |
| 数据会不会错乱/复活/串菜？ | 不会，有回归测试 |
| 首页是否只有一个主动作？ | 是，围绕今晚/录入 |
| 普通用户会看到工程信息吗？ | 不会 |
| 有付费理由吗？ | 有，家庭云同步 + OCR + 周计划 |

## 9. 外部参照

这些产品说明了同类赛道的基本能力边界：

- SuperCook：按已有食材找菜，强调减少浪费与利用现有食材。https://www.supercook.com/
- Samsung Food：围绕菜谱保存、计划、购物与 AI 个性化做厨房闭环。https://www.samsungfood.com/
- Mealime：主打个性化 meal plan 与 grocery list。https://www.mealime.com/
- SideChef：覆盖 meal planning、菜谱步骤和购物相关能力。https://www.sidechef.com/

Love-Kitchen 不应正面做“更大的菜谱库”，而应做更轻、更家庭、更贴近微信场景的厨房闭环。
